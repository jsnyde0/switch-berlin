## Login-wall middleware

Evolve the existing `ApprovalGateMiddleware` (in `accounts/middleware.py`, currently a pass-through) into the login-wall. This avoids adding a second middleware with overlapping concerns. At 0.4, the `is_staff` check relaxes to `is_approved`.

```python
class LoginWallMiddleware:
    PUBLIC_PATHS = {"/accounts/login/", "/accounts/logout/", "/healthz", "/robots.txt"}

    def __call__(self, request):
        if not getattr(settings, "LOGIN_WALL_ENABLED", True):
            response = self.get_response(request)
            response["X-Robots-Tag"] = "noindex, nofollow, noarchive"
            return response
        if request.path not in self.PUBLIC_PATHS and not request.user.is_authenticated:
            return redirect(f"/accounts/login/?next={request.path}")
        if request.user.is_authenticated and not request.user.is_staff:
            # 0.3 is staff-only; approved-but-not-staff users don't exist yet
            return HttpResponseForbidden("Not available yet.")
        response = self.get_response(request)
        response["X-Robots-Tag"] = "noindex, nofollow, noarchive"
        return response
```

Kill-switch: `LOGIN_WALL_ENABLED = True` in settings (default). Set to `False` in env to bypass during emergencies (ADR-003 F9).

At 0.4 this middleware relaxes to `user.is_approved`; at 0.5 it's removed from public routes entirely.

### `/events` list view

**Queryset:**
```python
Event.objects.filter(status="published", start__gte=now) \
    .select_related("organizer", "venue") \
    .prefetch_related("tags") \
    .order_by("start")
```

`select_related`/`prefetch_related` is required — without it, 40 events produce 120+ queries per page load, which pollutes the HTMX snappiness measurement driving the island decision gate.

**Partial rendering:** The list view detects `request.htmx` (via `django-htmx` middleware, already installed) and returns only the event list partial. Partials use Django native partials (Django 6.0+): define `{% partialdef event_list inline %}...{% endpartialdef %}` inside `list.html`; the full page renders the same block on initial load. No separate partial template files.

**Default sort:** `start ASC` where `start > now`.

**Filters:** render as DaisyUI badges; clicking toggles, HTMX re-fetches the list partial.

**Pagination:** default to pagination at 0.3 for simplicity (not infinite-scroll).

**URL state sync:** filter changes update `window.location.search` via `hx-push-url="true"`. When a filter changes, the page param resets to 1 (filter form's `hx-get` always omits `page` or sets `page=1`). Pagination links preserve all current filter params.

### Filter contract

| Param | Type | Example | Queryset effect | Empty/missing |
|-------|------|---------|----------------|---------------|
| `tags` | comma-separated slugs | `?tags=shibari,play-party` | OR semantics: `tags__slug__in=[...]` | No filter |
| `from` | ISO date | `?from=2026-05-01` | `start__date__gte` | No filter (no default) |
| `to` | ISO date | `?to=2026-05-31` | `start__date__lte` | No filter |
| `organizer` | slug | `?organizer=xyz` | `organizer__slug=` | No filter |
| `price` | `free` or `paid` | `?price=free` | `is_free=True` / `is_free=False` | No filter |
| `page` | integer | `?page=2` | Paginate | Default: 1 |

Unknown tag slugs are silently ignored (filtered to existing slugs before querying). Invalid param values (bad dates, non-integer page) fall back to defaults.

## Decision gate at end of phase

Answer one question: **does HTMX + Alpine carry `/events` cleanly, or do we need the React island?**

**Measurement:** Add `Server-Timing` header to HTMX partial responses (trivial middleware or decorator). Record timings during the dogfooding week. The "<100ms" threshold is measured server-side via `Server-Timing`, not subjective feel.

**Indicators HTMX is enough (→ cut island, revisit post-1.0):**
- Filter changes render list partial in <100ms (measured via `Server-Timing` header).
- Query-string state stays clean and shareable.
- No places where we had to write >20 lines of Alpine to coordinate two pieces of state.

**Indicators to ship the island at 0.4 (→ keep ADR-001 D5):**
- Multi-select filter + sort + pagination state got tangled.
- Anticipating the map view requires bidirectional sidebar↔map coupling that'll be ugly in Alpine.
- `hx-push-url` + filter history has edge cases (back button breaking).

Whichever way it goes, record the decision in a new ADR-004 at the end of the phase.

## Test plan

- View smoke tests: `/events`, `/events/<slug>`, `/o/<slug>` all return 200 for staff user.
- Login-wall: anonymous GET `/events` → 302 to `/accounts/login/`. Non-staff authenticated user → 403.
- Signup closed: GET `/accounts/signup/` → redirect or 403 (not a working form).
- Filter correctness: parameterized test asserts `?tags=X` filters the queryset correctly (OR semantics).
- Pagination + filter interaction: changing a filter resets to page 1.
- `robots.txt` served disallow-all; `X-Robots-Tag` header present on all responses.
- djlint passes on all new templates.
- Manual dogfooding checklist (see Feedback protocol below).

## Go/no-go to 0.4

**Code-complete criteria** (gate implementation work):
- All test plan items pass.
- HTMX-vs-island decision made and recorded as ADR-004.

**Content-ready criteria** (gate phase transition, but do not block 0.4 code work):
- At least 40 published events across 5 organizers (density check — if below, pause and forward more Telegram posts).
- Organizer-peer approves their profile page (see Feedback protocol).
- ≥5 staff/friend accounts browse `/events` across a week. Measured by: asking each person directly via Telegram ("did you browse this week?"). No analytics infrastructure needed at this scale.

If code-complete passes but content-ready lags, 0.4 code work may begin in parallel.

### Feedback protocol

Send organizer-peer a Telegram message with their `/o/<slug>` URL + 3 specific questions:
1. Is your name/description accurate?
2. Are your upcoming events correct?
3. What's missing?

Their response (any medium) is screenshot-archived. "Approves" = no factual errors reported OR all reported errors corrected and confirmed.

## Rollback

Rollback = revert:
1. `MIDDLEWARE` change in `settings.py` (login-wall middleware).
2. URL includes in `a_core/urls.py` (`events/` and `o/` routes).
3. Template files in `templates/events/`, `templates/organizers/`, and new `templates/cotton/` components.
4. Allauth adapter config (signup-closed).
5. `robots.txt` view in `a_core/urls.py`.

No migration rollback needed (no new models in 0.3). Login-wall can also be disabled via `LOGIN_WALL_ENABLED=False` without a full rollback.
