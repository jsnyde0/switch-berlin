# Roadmap: 0.1 → 1.0

**Date:** 2026-04-17
**Status:** Accepted
**Decisions:** [ADR-002](../decisions/ADR-002-phased-rollout-and-legal-gate.md), [ADR-003](../decisions/ADR-003-cheap-foresight-patterns.md)
**Target state:** [1.0 design](2026-04-17-v0-design.md) *(previously "V0 design" — scope is actually 1.0 soft-launch)*

## Purpose

The target-state design (`2026-04-17-v0-design.md`) describes everything the 1.0 soft-launch needs: ingestion, review, map, island, auth, signals, legal. That's a lot to build blind. This roadmap breaks the path to 1.0 into seven releasable milestones, each of which:

- Is usable end-to-end by *someone* (maintainer → one organizer-peer → ~5 insiders → invite list → public).
- Kills a specific risk that later phases depend on.
- Costs ≤2–4 weekends of solo-maintainer time.
- Includes kill-switches on any feature that expands the human-response surface.

## Organizing principles

1. **Pre-gate moves fast; post-gate doesn't.** Phases 0.1–0.3 are login-walled closed beta — not a public offering under DSA/JuSchG (see [ADR-002 D2](../decisions/ADR-002-phased-rollout-and-legal-gate.md)). Ship rough, break things, iterate. Everything after 0.5 is public and subject to the full legal checklist.
2. **Every deferred feature gets cheap foresight, not a stub.** See [ADR-003](../decisions/ADR-003-cheap-foresight-patterns.md). We don't build UI for phase N+2, but we do shape models, routes, and data capture so phase N+2 is additive, not a rewrite.
3. **Decisions are gated, not pre-committed.** Where a choice (e.g., React island vs. HTMX-only) can be made more cheaply after we've built the adjacent surface, we defer it to the phase where the evidence exists.
4. **Toil features ship with kill-switches.** Signup, signals, flags, organizer self-edit, and the public/invite toggle all need a runtime flag the maintainer can flip from admin in <30 seconds.

## The ladder

### 0.1 — Schema + admin + manual entry *(private)*

**Audience:** maintainer only.
**Scope:** Full normalized schema per ADR-001 D8. Django admin with bulk actions and inline raw↔parsed. Approval flag on User. No ingestion, no public surface, no auth. Manual entry of Event/Organizer/Venue to stress-test the model.
**Risk killed:** schema can't represent real Berlin events (recurring series, co-hosted, weird formats, privacy modes).
**Go/no-go to 0.2:** maintainer hand-enters ≥30 real events across ≥8 organizers without schema edits; zero fields feel like workarounds.
**Design doc:** [phase 0.1](2026-04-17-phase-0.1-schema-admin-design.md)

### 0.2 — Ingestion loop *(private)*

**Audience:** maintainer only.
**Scope:** Telegram bot ingests forwards from approved senders → `RawMessage`. URL enrichment (httpx + markdownify). pydantic-ai extraction → `EventDraft` → `Event(status=draft)`. Admin review UX with side-by-side diff and bulk approve. Capture GDPR consent fields on `Organizer` from day 1 even though nothing public consumes them yet (cheap foresight — see ADR-003).
**Risk killed:** LLM extraction isn't good enough; admin review exceeds 15 min/day budget.
**Go/no-go to 0.3:** over 2 weeks of real forwards, ≥70% of drafts approvable with ≤1 field edit; median review ≤20s/event; total daily admin ≤15 min at 10–20 events/day.
**Design doc:** [phase 0.2](2026-04-17-phase-0.2-ingestion-design.md)

### 0.3 — Internal /events, login-walled *(internal-only — NOT public under DSA)*

**Audience:** maintainer + 1 organizer-peer + 2–3 trusted friends (`is_staff` or hardcoded allowlist).
**Scope:** Server-rendered `/events` list, event detail, organizer profile, filters (date/tags/organizer). Authentication hard-wall: no anonymous read path exists. `robots.txt` disallow-all, no OG tags, no search indexing. The organizer-peer gets the link to their own `/o/<slug>` and sends corrections.
**Risk killed:** schema fails on a second human's events; HTMX surface is viable (or isn't); organizer cold-start is workable (or organizers won't engage, in which case 0.4+ is dead and we've learned it cheap).
**Decision gate at end of phase:** **React island — keep or cut?** If HTMX list+filter+event-detail feels fine, cut the island entirely and revisit post-1.0. If real seams appear (cross-panel state sync, filter URL state painful), commit to the island at 0.4. See [ADR-002 D3](../decisions/ADR-002-phased-rollout-and-legal-gate.md).
**Go/no-go to 0.4:** organizer-peer approves their page; ≥5 friends can browse without bugs; react-island decision made.
**Design doc:** [phase 0.3](2026-04-17-phase-0.3-internal-events-design.md)

### 0.4 — Map + filter surface *(internal-only, still login-walled)*

**Audience:** ~5–15 hand-picked insiders with invite codes.
**Scope:** `/events` gets the map view (MapLibre + OSM, neighborhood-blur circles, `privacy_mode` on Venue). If the 0.3 decision was "keep island," it ships here as React + django-vite; if "cut," HTMX+Alpine+MapLibre. allauth invite-token signup, but hard login-wall stays on. Attend/interested. Follow organizer (cheap, high-leverage engagement hook — promoted from 0.5 per synthesis).
**Risk killed:** map privacy model is broken; map is too empty to be useful at invite-gated density.
**Go/no-go to legal gate:** ≥3 private-venue organizers approve the blur as drawn; ≥40 published events; no organizer complaint about representation.
**Design doc:** [phase 0.4](2026-04-17-phase-0.4-map-invite-design.md)

### ══════ LEGAL GATE ══════

Before crossing into public (0.5), ship the compliance checklist as a single sprint. Agent-reviewed (per user's decision; no lawyer). Documented risk acceptance in ADR-002 D2. Checklist:

- JuSchG age gate (18+, cookie-persisted, pre-auth)
- DSA takedown endpoint + named contact + `/impressum`
- GDPR: lawful-basis record per organizer (data already captured from 0.2), opt-out endpoint, data-retention policy for `RawMessage`
- Terms, Privacy, Imprint pages
- Telegram bot consent text on first interaction
- Cookie policy (prefer session-only cookies to skip banner)
- Takedown inbox routed to filtered Gmail label (no ticketing system)

### 0.5 — Public read-only + invite accounts *(public — post-gate)*

**Audience:** anyone in Berlin can *read*; write requires invite-approved account.
**Scope:** `robots.txt` opens up, OG tags on; event/organizer pages become publicly linkable. Signup still invite-only. Organizer ratings DISPLAYED (threshold ≥3). Event ratings COLLECTED but hidden. Flag/report endpoint live with email-digest triage. Kill-switches on all toil features per ADR-002.
**Risk killed:** legal posture survives contact with real traffic; invite-gated signals have enough N to produce anything.
**Design doc:** [phase 0.5 (includes legal-gate checklist)](2026-04-17-phase-0.5-public-legal-design.md)

### 0.6 — Community signals mature *(public)*

**Audience:** same invite list, grown to ~50–80 users.
**Scope:** Signal thresholds tuned on real data. Event ratings still collected-only (waiting for per-event N). Organizer reviews surface in profile pages. (Auto-hide-on-N-flags rule shipped in 0.5 — pulled forward because flags without auto-hide create unbounded triage obligation.)
**Risk killed:** signals denoise; moderation scales to <10 min/day of flag triage.
**Design doc:** [phase 0.6](2026-04-17-phase-0.6-signals-design.md)

### 0.7 — Event reviews displayed *(public)*

**Audience:** same invite list, selectively expanded.
**Scope:** Event-level reviews unhide once per-event attendance density supports ≥3 threshold. Per-event reviews still gated behind attendance (must have `Attendance.status='went'` to review).
**Risk killed:** event reviews are signal, not noise; brigading doesn't destroy organizer relationships.
**Design doc:** [phase 0.7](2026-04-17-phase-0.7-event-reviews-design.md)

### 1.0 — Soft public launch *(public)*

**Audience:** Berlin, broadly — invite gate replaced by admin-reviewed signup form.
**Scope:** Admin-reviewed open signup. Organizer self-serve edits on their own upcoming events (edits to published events auto-revert to `status=review` if they touch price/date/venue; audit log). Bubble-bridging UI in filter surface. Logfire dashboards, rate-limiting, documented week-off runbook, "panic mode" toggle back to invite-only.
**Go signal:** 200 WAU within 6 weeks of launch; ≤15 min/day admin sustained; ≥6 active organizers; no legal complaint.
**Design doc:** [phase 1.0](2026-04-17-phase-1.0-soft-launch-design.md)

## Per-phase design docs

Each phase gets its own design doc written when the phase starts, not upfront. Naming:
`docs/plans/YYYY-MM-DD-phase-0.N-<name>-design.md`

The per-phase doc covers:
- Specific scope (what's in/out vs. this roadmap's scope line)
- Data-model deltas and migrations
- Concrete UI/API surface
- Test plan
- Rollback plan if the phase's go-signal isn't hit

The target-state design (`2026-04-17-v0-design.md`) stays the north star — per-phase docs reference it rather than duplicate it.

## What got cut from the target state

From the synthesis: **pgvector columns** (extension stays, no `VectorField` until a feature needs it), **in-app flag triage UI** (replaced with email digest), **signal-driven cached follower counts** (nightly recompute), **event-level reviews DISPLAYED before 0.7** (they're collected from 0.5 but hidden). These are deferred per ADR-003's cheap-foresight pattern, not removed from the 1.0 target.
