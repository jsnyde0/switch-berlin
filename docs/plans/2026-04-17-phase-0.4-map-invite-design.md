## 0.3 outcomes (context for this phase)

Phase 0.3 shipped: login-wall (`LoginWallMiddleware` in `accounts/middleware.py`), signup-closed (`NoSignupAdapter`), `/events` list with HTMX filters + `template_partials` + Alpine tag toggle, `/events/<slug>` detail, `/o/<slug>` organizer profile, Cotton components, Server-Timing on HTMX partials, 21 integration tests. Key implementation details that affect 0.4:

- **Middleware:** `LoginWallMiddleware` (not `ApprovalGateMiddleware` — the stub was replaced). Uses prefix matching on `PUBLIC_PREFIXES`. Kill-switch: `LOGIN_WALL_ENABLED` env var. At 0.4, relax the `is_staff` check to `is_approved`.
- **Signup:** Closed via `NoSignupAdapter` (`accounts/adapter.py`). The invite flow must conditionally re-open signup when a valid invite code is present (override `is_open_for_signup` to check for code in session/GET param).
- **Event URL scheme:** Currently `/events/<slug>/` where slug is only unique per-organizer (not globally). Two organizers with the same event slug cause a 500. **0.4 must fix this** — change to `/events/<org-slug>/<event-slug>/` or enforce global slug uniqueness. This affects the event card component, detail view, and all URL references.
- **CSRF for HTMX:** `_base.html` body tag has `hx-headers='{"X-CSRFToken": "{{ csrf_token }}"}'`. POST-based HTMX interactions (attend, follow) will work out of the box.
- **Cotton components:** Use `:prop="var"` syntax (colon prefix) for Python objects. Established components: `event_card`, `organizer_mini_card`, `filter_chips`, `pagination`.
- **HTMX partials:** `template_partials` with `{% partialdef name inline %}` blocks. HTMX requests detected via `request.htmx` (django-htmx middleware).
- **Login template:** "Register" link removed (signup is closed). Restore or add invite-code-aware link at 0.4.

class Attendance(models.Model):
    user = FK(User, on_delete=CASCADE, related_name="attendances")
    event = FK(Event, on_delete=CASCADE, related_name="attendances")

## Map surface

- MapLibre GL JS. Tiles: OSM community server or self-hosted tileserver-gl (decide at phase start; if self-hosted, add to Compose).
- Default view: Berlin center, zoom 11.
- Pins for public venues; circles for private venues; cluster at low zoom.
- Clicking pin/circle → opens event detail in side-drawer (no page navigation).
- Neighborhood-blur: circle is rendered in place of the pin at all zoom levels for privacy venues. Exact coordinates NEVER sent to the client for private venues unless user has `Attendance.status='going'`.

### Privacy enforcement (server-side)
- Venue serializer: if `privacy_mode='private'` AND requesting user doesn't have `Attendance(event__venue=v, status='going')`, return blurred center (rounded to 3 decimal places of lat/lng, picked deterministically from venue slug hash) + radius.
- Never trust the client.

## Implementation — HTMX default (per ADR-004)

- Map is a vanilla MapLibre instance initialized on page load inside `<div id="map" hx-preserve="true">`. The map container is never swapped by HTMX.
- Filter changes re-fetch the list partial AND ship a fresh GeoJSON payload (via `{{ markers|json_script }}` sibling block), then emit a `events:filter-changed` window event the map listens for.
- Cross-panel state (selection, hovered event, bounds) lives in a single `Alpine.store('map', …)`. Components talk via custom window events (`events:selection-changed`, `events:bounds-changed`), never via shared closures.
- Side-drawer event detail via `hx-target="#drawer"`.
- Map container, store, and event-bus are designed as a **swappable surface** — see ADR-004 D3. If post-1.0 a feature requires deck.gl reverse-control or a React-first map plugin, the `#map` element can be replaced with a React island mounted on the same events without touching filter chips, list, or drawer.

See the [Phase 0.4 HTMX map spike design](2026-04-20-phase-0.4-htmx-map-spike-design.md) for the executable validation plan, the T1–T5 tripwires, and the React-island fallback protocol.

## Invite flow

```
Maintainer admin: "Generate 10 invite codes" → 10 InviteCode rows
Maintainer DMs code to Anna
Anna visits /accounts/signup/?code=XXXX
  → allauth signup form (email, password, display name)
  → on signup, InviteCode.redeemed_by=anna
  → User.is_approved=False initially
Maintainer admin: sees Anna in "needs approval" queue → approves
  → User.is_approved=True → Anna can now access /events
```

## Test plan

- Privacy enforcement: user without `going` Attendance CANNOT see private venue's exact coords via the JSON API. Parameterized across all access paths.
- Invite code redemption: unique-use (redeemed code rejects second redemption); expired code rejected.
- `LoginWallMiddleware`: anonymous → redirect; `is_approved` user → allowed; `is_staff` user → also allowed (backward-compat with 0.3 staff accounts). Verify middleware correctly relaxed from `is_staff` to `is_staff or is_approved`.
- Map smoke test: page renders with ≥1 marker at staff zoom.
- Hover coupling test (if JS): event card hover adds `.highlighted` class to corresponding pin.
- E2E walkthrough: invite-code flow → signup → approval → browse map → attend event → see correct private-venue coords.

## Go/no-go to legal gate

- ≥3 private-venue organizers approve the blur as drawn (DM them a screenshot; verbal ok).
- ≥40 published events so the map isn't sad.
- No organizer complaint about their representation on the map.
- Attendance + follow working; no user has managed to bypass privacy enforcement.

## Rollback

- Flip `MAP_ENABLED=False` env var → template hides map tab; list-only view.
- Flip `INVITES_ENABLED=False` → signup form 503s; existing accounts still work.
- Attendance and follow rows persist; removing buttons doesn't lose data.
