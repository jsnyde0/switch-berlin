## 0.3 outcomes (context for this phase)

Phase 0.3 shipped: login-wall (`LoginWallMiddleware` in `accounts/middleware.py`), signup-closed (`NoSignupAdapter`), `/events` list with HTMX filters + `template_partials` + Alpine tag toggle, `/events/<slug>` detail, `/o/<slug>` organizer profile, Cotton components, Server-Timing on HTMX partials, 21 integration tests. Key implementation details that affect 0.4:

- **Middleware:** `LoginWallMiddleware` (not `ApprovalGateMiddleware` — the stub was replaced). Uses prefix matching on `PUBLIC_PREFIXES`. Kill-switch: `LOGIN_WALL_ENABLED` env var. At 0.4, relax the `is_staff` check to `is_staff or is_approved`. **Note:** The current `is_staff` check sits outside the `PUBLIC_PREFIXES` guard, so the fix is a ~5-line restructure (move the check inside the `if not any(...)` block), not just a predicate swap.
- **Signup:** Closed via `NoSignupAdapter` (`accounts/adapter.py`). The invite flow must conditionally re-open signup when a valid invite code is present (override `is_open_for_signup` to check for code in session/GET param).
- **Event URL scheme:** Currently `/events/<slug>/` where slug is only unique per-organizer (not globally). Two organizers with the same event slug cause a 500. **0.4 must fix this** — change to `/events/<org-slug>/<event-slug>/` or enforce global slug uniqueness. This affects the event card component, detail view, and all URL references.
- **CSRF for HTMX:** `_base.html` body tag has `hx-headers='{"X-CSRFToken": "{{ csrf_token }}"}'`. POST-based HTMX interactions (attend, follow) will work out of the box.
- **Cotton components:** Use `:prop="var"` syntax (colon prefix) for Python objects. Established components: `event_card`, `organizer_mini_card`, `filter_chips`, `pagination`.
- **HTMX partials:** `template_partials` with `{% partialdef name inline %}` blocks. HTMX requests detected via `request.htmx` (django-htmx middleware).
- **Login template:** "Register" link removed (signup is closed). Restore or add invite-code-aware link at 0.4. **Note:** The navbar (`cotton/navbar.html`) still has a "Register" link for unauthenticated users — conditionally show it only when `INVITES_ENABLED` is true.
- **Pre-existing bugs to fix at 0.4 start:**
  - `organizers/views.py` uses `organizer.event_set` but the FK has `related_name="events"` — runtime crash on `/o/<slug>`. Fix: change to `organizer.events`.
  - `pagination.html` targets `#event-list-container` but the actual DOM element is `#event-list` — HTMX pagination silently fails. Fix: align the target IDs.

## Data model deltas

### `events.Attendance`
```python
class Attendance(models.Model):
    user = FK(User, on_delete=CASCADE, related_name="attendances")
    event = FK(Event, on_delete=CASCADE, related_name="attendances")
    status = CharField(choices=[("interested","Interested"),("going","Going"),("went","Went")], default="interested")
    created_at = DateTimeField(auto_now_add=True)
    updated_at = DateTimeField(auto_now=True)

    class Meta:
        unique_together = [("user","event")]
```

### `organizers.OrganizerFollow`
```python
class OrganizerFollow(models.Model):
    user = FK(User, on_delete=CASCADE, related_name="follows")
    organizer = FK(Organizer, on_delete=CASCADE, related_name="followers")
    created_at = DateTimeField(auto_now_add=True)

    class Meta:
        unique_together = [("user","organizer")]
```

### `accounts.InviteCode`
```python
import secrets

def generate_code():
    return secrets.token_urlsafe(24)  # ~32 chars, 192 bits entropy

class InviteCode(models.Model):
    code = CharField(max_length=48, unique=True, default=generate_code)
    created_by = FK(User, on_delete=PROTECT, related_name="invites_created")  # PROTECT: audit trail
    created_at = DateTimeField(auto_now_add=True)
    redeemed_by = FK(User, null=True, blank=True, on_delete=SET_NULL, related_name="invite_redeemed")
    redeemed_at = DateTimeField(null=True, blank=True)
    expires_at = DateTimeField(null=True, blank=True)
    notes = TextField(blank=True)  # "for Anna at Shibari Club"
```

**Single-use by design:** Each code has one `redeemed_by` FK slot. Multi-use codes (e.g., meetup batch codes) would require a separate `InviteRedemption` join table — not needed at 0.4 scale, bounded cost to add later.

**Batch generation:** Via management command `generate_invite_codes --count N --notes "batch for April meetup"`. Admin UI shows code list with redemption status.

No caches or denormalized counts yet (F8: counts come via nightly recompute at 0.6 if needed).

## Map surface

- MapLibre GL JS. Tiles: OpenFreeMap liberty style (`tiles.openfreemap.org/styles/liberty`), already shipped in the graduated spike.
- Default view: Berlin center, zoom 11.
- Pins for public venues; circles for private venues; cluster at low zoom.
- Clicking pin/circle → opens event detail in side-drawer (no page navigation).
- Neighborhood-blur: circle is rendered in place of the pin at all zoom levels for privacy venues. Exact coordinates NEVER sent to the client for private venues unless user has `Attendance.status='going'`.

### Privacy enforcement (server-side)
- Venue serializer signature: `venue_to_geojson(venue, *, going_venue_ids=None)`. The view pre-fetches the set of venue IDs where the requesting user has `Attendance(status='going')` as a single query, passes that set through. When `going_venue_ids` is None or empty, always blur (backwards-compatible with current behavior). This keeps the serializer stateless — no user object leaks into the data layer.
- Coordinate privacy: if `privacy_mode='private'` AND requesting user doesn't have `Attendance(event__venue=v, status='going')`, return blurred center (rounded to 3 decimal places of lat/lng, picked deterministically from venue slug hash) + radius.
- **Venue metadata visibility:** For `privacy_mode='private'`, templates display "Private venue" instead of the venue name, and suppress the neighborhood field, unless the requesting user has `Attendance(status='going')`. For `neighborhood_blur`, the venue name is shown but the address is suppressed (only neighborhood). For `public`, all fields shown. This requires template-level conditionals in `event_card`, `detail.html`, and `_event_drawer.html`.
- Never trust the client.

## Implementation — HTMX default (per ADR-004)

- Map is a vanilla MapLibre instance initialized on page load inside `<div id="map" hx-preserve="true">`. The map container is never swapped by HTMX.
- Filter changes re-fetch the list partial AND ship a fresh GeoJSON payload (via `{{ markers|json_script }}` sibling block), then emit a `events:filter-changed` window event the map listens for.
- Cross-panel state (selection, hovered event, bounds) lives in a single `Alpine.store('map', …)`. Components talk via custom window events (`events:selection-changed`, `events:bounds-changed`), never via shared closures.
- Side-drawer event detail via `hx-target="#drawer"`.
- Map container, store, and event-bus are designed as a **swappable surface** — see ADR-004 D3. If post-1.0 a feature requires deck.gl reverse-control or a React-first map plugin, the `#map` element can be replaced with a React island mounted on the same events without touching filter chips, list, or drawer.

See the [Phase 0.4 HTMX map spike design](2026-04-20-phase-0.4-htmx-map-spike-design.md) for the executable validation plan, the T1–T5 tripwires, and the React-island fallback protocol.

## Invite flow

```
Maintainer runs: python manage.py generate_invite_codes --count 10 → 10 InviteCode rows
Maintainer DMs code to Anna
Anna visits /accounts/signup/?code=XXXX
  → allauth signup form (email, password, display name)
  → on signup, InviteCode.redeemed_by=anna (atomic — see below)
  → User.is_approved=False initially
  → Anna sees pending-approval page (not a bare 403)
Maintainer admin: sees Anna in "needs approval" queue → approves
  → User.is_approved=True → Anna can now access /events
```

### Atomic code redemption
Code redemption uses `InviteCode.objects.filter(code=code, redeemed_by__isnull=True).update(redeemed_by=user)` inside a `transaction.atomic()` block. If the update returns 0 rows (race: code redeemed between form render and submit), log a warning and continue — allauth's `save_user` cannot safely reject after user creation without causing 500s. The second user is created with `is_approved=False` and no redemption record; staff reconcile manually. Acceptable at 0.4 scale (5-15 users).

### Approval-pending state
Users who sign up via invite but are not yet approved (`is_authenticated=True, is_staff=False, is_approved=False`) see a `403_pending_approval.html` template with messaging like "Your account is pending approval. You'll receive an email when approved." `PUBLIC_PREFIXES` (including `/accounts/` sub-paths for logout, password change) remain accessible to all authenticated users regardless of approval status — this requires the middleware restructure noted in 0.3 outcomes.

## Follow + attend interactions

### URL patterns
- Attend: `POST /events/<int:event_id>/attend/` (consistent with existing drawer endpoint PK pattern). Returns HTMX partial swap of button state.
- Follow: `POST /o/<slug>/follow/`. Returns HTMX partial swap of button state.
- CSRF already configured in `_base.html` via `hx-headers`.

### Attend states
- "Interested" and "Going" are always available. "Went" is only available after `event.start` has passed — the template conditionally shows it. Before the event, the UI shows "Interested" and "Going" only. (Alternative: defer "Went" entirely to 0.5 when reviews ship, since "went" is a natural prerequisite for reviewing.)
- No counts shown publicly at 0.4 (F8 nightly recompute doesn't exist yet; raw queryset count is fine at this scale).

### Map integration (ADR-004 D3 compliance)
When a user marks "Going" on an event with a private venue, the map should update to show exact coordinates. After a successful attend POST, the server returns an `HX-Trigger: events:attendance-changed` response header. The map module listens for this event and re-fetches marker data. This follows ADR-004 D3's event-bus discipline — all cross-component communication via custom DOM events on `window`.

## Test plan

- Privacy enforcement (coordinates): user without `going` Attendance CANNOT see private venue's exact coords via the JSON API. Parameterized across all access paths.
- Privacy enforcement (venue metadata): private venue's name and neighborhood are NOT rendered in event card, detail page, or drawer for users without `going` Attendance. Template shows "Private venue" instead.
- Invite code redemption: unique-use (redeemed code rejects second redemption); expired code (`expires_at` in the past) rejected even if unredeemed. Atomic: two simultaneous signups with same code result in at most one redemption.
- `LoginWallMiddleware`: anonymous → redirect; `is_approved` user → allowed; `is_staff` user → also allowed (backward-compat with 0.3 staff accounts). Verify middleware correctly relaxed. Verify `PUBLIC_PREFIXES` remain accessible to all authenticated users (including unapproved).
- Approval-pending UX: signed-up-but-not-approved user sees `403_pending_approval.html`, not a bare 403 string.
- Attend/follow CSRF: POST to attend/follow endpoints without CSRF token returns 403.
- Attend/follow auth: unauthenticated and unapproved users cannot POST to attend/follow endpoints.
- Map smoke test: page renders with ≥1 marker at staff zoom.
- Hover coupling test (if JS): event card hover adds `.highlighted` class to corresponding pin.
- E2E walkthrough: invite-code flow → signup → approval → browse map → attend event → see correct private-venue coords.
- Kill-switch tests: `MAP_ENABLED=False` hides map; `INVITES_ENABLED=False` disables invite signup.

- ≥3 private-venue organizers approve the blur as drawn (DM them a screenshot; verbal ok).
- ≥40 published events so the map isn't sad.
- No organizer complaint about their representation on the map.

## Migration and deploy order

Migrations run in order: `accounts.InviteCode` → `events.Attendance` → `organizers.OrganizerFollow`. Feature flags gate UI independently. A half-migrated state (InviteCode exists, Attendance does not) must not crash any view — the attend/follow buttons are gated by `MAP_ENABLED` / model existence checks.

## Rollback

- Flip `MAP_ENABLED=False` env var (`env.bool("MAP_ENABLED", default=True)` in settings) → template hides map div and map JS; list-only view.
- Flip `INVITES_ENABLED=False` env var (`env.bool("INVITES_ENABLED", default=True)` in settings) → signup adapter rejects invite codes; existing accounts still work. Navbar hides "Register" link.
- Attendance and follow rows persist; removing buttons doesn't lose data.
- Both flags must be implemented as explicit 0.4 deliverables (per ADR-003 F9), not assumed to exist.
