# Design: V0 — Queer/Conscious Kinky Berlin Events Site

**Date:** 2026-04-17
**Status:** Draft
**Decisions:** [ADR-001](../decisions/ADR-001-core-product-and-stack.md)
**Origin:** Brainstorm following two stalled prior attempts (`event-gulper` pipeline + `just-show-up` scaffold). **Supersedes:** `docs/project_brief.md` (partial — keeps audience; deprecates firehose-ingestion architecture)

---

## Problem

The Berlin queer/kink event scene is fragmented across many Telegram channels, each run by a different organizer or collective. Finding what's on requires already belonging to the right bubbles. Newcomers don't know which channels to trust. Locals miss adjacent scenes they'd otherwise enjoy. Generic listings sites have failed to fill the gap: Telegram is strictly better for people already plugged in, and open-marketplace models drift toward spam or value-dilution.

Two prior repos — `event-gulper` (a Prefect/FastAPI/SQLAlchemy pipeline that shipped one working Siegessäule source) and `just-show-up` (a Django 5 + HTMX + Tailwind scaffold with a parallel CrewAI/controlflow scraper) — diverged, duplicated work across incompatible stacks, and died before shipping. Neither delivers the product; both contain salvageable pieces.

The product gap is **trust**, not listings. A curated aggregator with values-aligned organizer vetting and community-driven event surfacing is a product Telegram structurally cannot be.

## Goal

Ship a V0 that makes approved queer/conscious-leaning Berlin organizers' events browsable, filterable, and mappable in one surface. Community signals from approved users — not editorial picks — decide which events rise. The editor's job is gating organizers (bounded work), not curating weekly content.

## Non-Goals

- Multi-city. Berlin-only for 12 months; no abstraction for other locales until ≥3 volunteer curators offer to run them.
- Editor's-pick cards, weekly editor's notes, per-organizer curator notes. Community signals replace editorial voice.
- Open marketplace. Organizer onboarding is relationship-based, not a self-serve form.
- Manual event-level moderation. Editor is hands-off once an organizer is approved; per-event action is exception-driven (flags trigger a conversation with the organizer).
- Broad sex-positive scope (tantra, ecstatic dance). Dilutes the wedge into Hipsy's territory.
- Ticketing. Deferred past V3.
- OCR, roundup-post splitting, login-gated crawlers (Fetlife, IG), Telethon user-session scraping. V0 deferrals.
- Bubble-bridging UI. Schema supports it; UI ships V1.

## Proposed Architecture

Monolithic Django 5 application with four Django apps (`accounts`, `events`, `organizers`, `scraping`), Postgres 16 with pgvector, and Django-Q 2 for background work. One page (`/events`) is a React 19 island mounted via `django-vite`; every other page is server-rendered Django + HTMX + django-cotton.

```
Telegram forward
  (approved organizer → bot, OR editor → bot from channels they lurk in)
    → bot stores RawMessage (text, media refs, extracted URLs, sender, channel, ts)
    → URL enrichment: fetch each URL (httpx) → markdownify
    → pydantic-ai extract: structured EventDraft
    → creates Event (status=draft) linked to RawMessage
    → admin review queue (Django admin, customized)
    → admin approves / edits / rejects
    → published (status=published)
```

### Trust model (two tiers)

1. **Organizer trust — admin-gated.** Editor manually vets and approves organizers before they can submit events. Relationship-based, not form-based. "Verified" = admin-approved; there are no unverified organizers in V0.
2. **Event attention — community-gated.** Approved users signal *interested / going / attended*, like/dislike, and leave reviews on organizers and events. These signals drive default sort and surface-ability.

Consequence: editor workload is bounded (vet new organizers, occasionally review flags) rather than per-event.

### Ingestion pipeline

- **Telegram bot** (`python-telegram-bot`): runs as a long-lived Django-Q 2 scheduled worker or a management command under a supervisor. Handles forwards from approved senders; stores `RawMessage` rows.
- **URL enrichment**: `httpx` + `beautifulsoup4` + `markdownify` — ported from `event-gulper/transforms/scrape.py`, stripped of Prefect decorators. Fetches each URL found in a Telegram post and converts to clean markdown for extraction.
- **LLM extraction**: `pydantic-ai` only. Structured `EventDraft` schema with per-field null allowed; missing fields prompt the editor to fill them in during review. Retries use pydantic-ai's built-in mechanism.
- **One pipeline, one extraction model.** No raw/normalized split; `Event.status` lifecycle (draft → review → published → rejected/cancelled) replaces that machinery. `RawMessage` is the audit log.

### Public UX

**Single `/events` surface.** No separate homepage. Landing is "what's on in Berlin, sorted by date ascending" unless the user has a persisted preference.

`/events` is a **React island** mounted in a Django shell via `django-vite`. Initial state (filters, user prefs, CSRF token) passes from Django to React via `{{ ... |json_script }}`; the island fetches `/api/events?…` with session cookies — no JWT, no CORS. Tailwind v4 + DaisyUI share a single `app.css` across Django templates and the island. See ADR-001 D5 for why this page is islanded and the rest is not.

**Filters** (all query-param, bookmarkable, stored in session for anon and `User.prefs` for authenticated):
- Date range (default: today → +14 days)
- Tags (shibari, impact, workshop, party, munch, queer, etc.)
- Organizer
- Price: free / paid / any
- View mode (list / map)

**List view**: event cards — cover image, date, title, organizer name + face, venue-or-neighborhood, price, tag chips, community signals (N interested, M going, ★ rating if ≥3 reviews).

**Map view**: MapLibre GL + OSM tiles. AirBnB-style neighborhood circles for events whose venue opts for privacy (`privacy_mode=neighborhood_blur`). Pins for public venues. `privacy_mode=private` ("location revealed after RSVP") gets a broad ~1km circle in the roughly-correct neighborhood.

**Event detail page**: cover image, title, localized time, venue (or neighborhood blur), tags, price, external CTA to organizer/ticket page, organizer mini-card, save/attend/flag buttons, report link. Description rendered from stored markdown.

**Organizer profile** (`/o/<slug>`): face, bio, banner, upcoming events, past events, community review aggregate, "verified" badge. Contact handles (Telegram, IG) as links.

### Data model

All entities in the Django ORM.

- **User** (`AbstractUser` or profile extension): `is_approved`, `approved_at`, `approved_by`, `prefs (JSONB)`, `interests (M2M Tag)`.
- **Organizer**: `slug (unique)`, `name`, `bio_md`, `profile_image`, `banner_image`, `verified_at`, `contact_handles (JSONB)`, `review_aggregate_score (cached)`, `review_count (cached)`, `follower_count (cached)`.
- **Venue**: `name`, `privacy_mode (public|neighborhood_blur|private)`, `address (optional)`, `geo_point (PostGIS Point, optional; lat/lng columns fallback)`, `neighborhood`, `url`.
- **Event**: `organizer_fk`, `venue_fk (nullable)`, `title`, `description_md`, `description_html (cached)`, `cover_image`, `start (tz-aware)`, `end (nullable, tz-aware)`, `price_min (Decimal)`, `price_max (Decimal)`, `currency (default EUR)`, `tags (M2M Tag)`, `external_url`, `status (enum: draft|review|published|rejected|cancelled)`, `raw_message_fk (nullable)`, `embedding (pgvector, async-filled)`.
- **Tag**: `slug (unique)`, `label`, `kind (theme|format|identity|accessibility|bubble)`.
- **RawMessage**: `telegram_channel`, `telegram_msg_id`, `text`, `media_refs (JSONB)`, `extracted_urls (JSONB)`, `received_at`, `parsed_event_fk (nullable)`, `extraction_errors (JSONB)`.
- **Attendance**: `user_fk`, `event_fk`, `status (interested|going|attended)`, `created_at`. Unique on `(user, event)`.
- **Review**: `user_fk`, `target_type (organizer|event)`, `target_id`, `rating (1..5)`, `text`, `created_at`.
- **Flag**: `user_fk`, `target_type`, `target_id`, `reason`, `status (open|resolved)`, `created_at`.
- **Follow**: `user_fk`, `organizer_fk`, `created_at`.

**Cached counts on Organizer** (review aggregate, follower count): common-read, rare-write; update via signals on Review/Follow/Attendance save.

### Repo strategy

Start from **`just-show-up`** (more mature scaffold: allauth, cotton, HTMX, Tailwind, Docker, CI), not `event-gulper`.

1. New branch `rebuild/v0` on `just-show-up`.
2. Rename project (name TBD — placeholder `berlin-kink-site` during build).
3. **Delete**: controlflow, CrewAI, Celery, celery-beat, Redis, admin-honeypot, Cloudinary, stub views in `events/views.py`.
4. **Port from `event-gulper`** (stripped of Prefect decorators):
   - `pipeline/core/transforms/scrape.py` → `scraping/enrichment.py`
   - `pipeline/core/transforms/llm.py` → `scraping/extraction.py`
   - `pipeline/core/sources/siegessaeule.py` → archive; useful only for discovering candidate organizers, not for ingestion.
5. **Squash old migrations**; new initial migration with the V0 schema above.
6. **New Django apps**: `accounts`, `events`, `organizers`, `scraping`.
7. **Admin review UX**: Django admin with inline RawMessage ↔ Event link, bulk actions (approve N drafts at once), side-by-side raw-vs-parsed diff.
8. **Delete `event-gulper`** once rebuild is stable and migrated.

## Key Design Decisions

See [ADR-001](../decisions/ADR-001-core-product-and-stack.md) for full rationale, alternatives tables, and invalidation criteria. Summary:

- **D1** — Curated-trust, community-surfaced framing (not editorial magazine, not open marketplace)
- **D2** — Berlin insiders first, 12-month scope lock
- **D3** — No manual event-level curation
- **D4** — User accounts are V0-load-bearing
- **D5** — Single `/events` surface as React island via `django-vite`; rest of site server-rendered Django + HTMX
- **D6** — Django monolith + Django-Q 2 + pydantic-ai + Postgres+pgvector; drop Celery/Prefect/SQLAlchemy/instructor/controlflow/CrewAI
- **D7** — Merge from `just-show-up` scaffold; port 3 files from `event-gulper`
- **D8** — Normalized schema from day 1
- **D9** — Telegram bot + URL enrichment + pydantic-ai + admin review
- **D10** — Legal compliance (JuSchG, DSA, GDPR) is critical path before public launch

## Consequences

**Easier:**
- One deploy target, one language for web + ingestion
- Django admin handles the review UX for free — load-bearing for two-tier trust
- allauth handles auth flows
- Schema normalized up front — no mid-V1 migration when organizer profiles need aggregate queries
- Admin workload bounded by design (no per-event curation)
- Legal obligations (age gate, takedown, consent) scoped to a checklist, not retrofitted

**Harder:**
- Two frontend mental models (HTMX + Django templates most places, React on `/events`) — mitigated by isolating the island and sharing Tailwind/DaisyUI across both
- pgvector adds a Postgres extension to manage
- Cold-start depends on relationship-based organizer onboarding — slow and unscalable by design

**Tradeoffs:**
- Niche scope limits growth ceiling vs. a generic aggregator — but niche is why the product works at all
- Hands-off editor means no "curated this week" voice — the tradeoff explicitly chosen
- Django admin looks dated visually — acceptable because it's editor-facing, not public

## Known Limitations

- Siegessäule scraper is archived; useful for discovering candidate organizers but not active in V0 ingestion. Reactivate if organizer cold-start stalls.
- AirBnB-style neighborhood circle is an imperfect privacy model (Berlin neighborhoods vary in size); V0 ships with it and iterates.
- pydantic-ai extraction will sometimes return partial or missing fields; admin review compensates, but high draft volume could overwhelm one editor.
- Community signal noise floor is unknown at low user counts. Mitigation: hide signals below thresholds (≥3 ratings, ≥5 attendances).
- Solo maintainer risk: everything collapses if one person's time runs out. Mitigation: hands-off architecture; admin review queue time-boxed ≤15 min/day.
- Cold-start risk: approved organizers must exist before bot is useful. Mitigation: editor runs bot-forward from lurked channels for the first 4–6 weeks; relationship-based onboarding in parallel.

## Open Questions

1. **Name** — "Event Gulper" dropped. Placeholder during build. Candidates: `kink.berlin`, `Kompass`, `Scene`, `afterdark.berlin`. Pick before soft-launch.
2. **Hosting** — default Hetzner VPS + Docker Compose. Cheap, PostGIS/pgvector friendly, full control. Revisit if scaling limits hit.
3. **PostGIS vs lat/lng columns** — default lat/lng for V0. PostGIS only if map-query complexity demands it.
4. **Organizer granularity** — per-collective/promoter, not per-venue. Venue and Organizer are separate; one venue hosts many organizers. (Resolved as default.)
5. **Telegram ingestion mode** — bot forwards only for V0. No Telethon user-session scraping. (Resolved as default.)
6. **User signup gate** — invite-only at V0 launch; admin-reviewed signup form once invite list is exhausted. (Resolved as default.)
7. **Map provider** — default MapLibre + OSM. Mapbox only if OSM rendering proves inadequate.
8. **Bubble as first-class entity vs Tag** — Tag with `kind=bubble` for V0. Promote to own model when the bridging UX ships.
9. **HTMX vs Datastar for non-island pages** — default HTMX + Alpine.js + django-htmx + django-template-partials + Idiomorph (battle-tested 2026 combo). Datastar (2026 alternative: signals + SSE in one 14KB library, no HTMX/Alpine seam) is worth re-evaluating at V1 if the Alpine/HTMX seam proves painful. Not a V0 blocker — the React island isolates the hardest interactive surface.
10. **Tailwind pipeline** — `node/` vs `django-tailwind-cli`. Evaluate during scaffold cleanup; not a blocker.
